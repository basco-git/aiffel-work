## Q2. 업리프트는 AUC와 관점이 다른데 교안 내용을 반영할 수 있나? (2026-11-16)

사용자 질문: 다른 분석법은 AUC 기반인데 업리프트는 다른 관점이라, 교안에 쓰던 내용을 반영할 수 있는가?

교안 17번 1파트(표와 평가)와 6파트(도입 판단)를 읽고 대조했다.

### 교안 개념이 그대로 이어지는 부분

| 교안 17번 개념 | 업리프트에서의 쓰임 |
|---|---|
| 기준선 (1파트): 새 모델이라는 이유만으로 더 나은 선택이 아님 | **위험 점수 순 선정이 업리프트의 기준선**이 된다. "효과 순이 위험 순보다 정말 나은가?"를 비교 |
| 같은 시험 자료 (1파트) | 위험 모델과 업리프트 모델 모두 같은 시험 행, 같은 k로 비교 |
| AUC는 순서를 본다 (1파트) | 업리프트의 순서 평가 지표는 Qini 곡선. "누구를 먼저 줄 세우나"는 같고 대상이 "떠날 사람" → "면담하면 남을 사람"으로 바뀜 |
| 문턱은 사람이 정한다 (1·6파트) | 상위 k% 슬라이더 그대로 사용 |
| 점수를 업무 피해와 연결 (6파트) | 비용 식이 그대로 이어짐. 모두에게 같던 성공률 `r`을 사람마다 다르게 다룰 수 있음 |
| 작게 시작, 지난 기록과 비교 (6파트) | 업리프트 학습에는 "일부를 무작위로 면담해 본 기록"이 필요 → 실제 도입 절차(시범 운영) 설명으로 연결 |

### 교안에 없어서 새로 설명해야 하는 부분

1. **정확도·AUC로 업리프트를 채점할 수 없다.** 한 사람은 면담을 받았거나 안 받았거나 둘 중 하나뿐이라 개인 단위의 "효과 정답"이 없다. 이를 설명하는 카드와 Qini 곡선 설명이 추가로 필요하다.
2. **가상 데이터라 결과가 설계에 좌우된다.** "위험은 높지만 이미 마음을 굳힌 사람"을 규칙으로 넣으면 업리프트가 이기는 것은 당연하다. 그래서 두 시나리오를 함께 보여 준다.
   - 효과가 모두 같은 시나리오: 위험 순으로 충분하다. 교안의 "비슷하면 간단한 방법"과 같은 결론이다.
   - 효과가 사람마다 다른 시나리오: 업리프트가 나을 수 있다.
   - 가상 데이터라서 **진짜 개인별 효과를 알고 있으므로**, 실제 자료로는 불가능한 검증(추정 효과와 진짜 효과 비교)을 할 수 있다.

### 결정 (사용자 승인)

- **1단계(교안 그대로):** 위험 예측 모델 비교. 기준선, 같은 시험 자료, 정확도·AUC, 문턱
- **2단계(교안 확장):** 위험 순과 면담 효과 순 비교. 기준선은 1단계 위험 점수, 지표는 Qini와 순이익. 화면에 "교안 밖 확장"으로 표시
- 효과 시나리오 2종(균일 / 사람마다 다름)을 함께 제시
- **확률 보정 포함:** 기대이익 계산에 필요하므로 자동으로 함께 넣는다
- PRD 반영 시 바뀌는 곳(예정): §5 데이터(면담 여부 무작위 배정, 개인별 효과, 시나리오 매개변수), §6 모델링(업리프트 모델, 보정), §7 비용 계산(개인별 효과 반영), §8 기능(설명 카드·Qini 곡선 추가), §12 작업 목록과 일정

## Q7. 제출 형식과 T1 위험 확인 (2026-11-16)

- **제출 형식:** 기존 과제와 같다. 제출 링크를 내고, `aiffel-work` 맨 위 README 과제 목록과 과제 폴더 README에 기록을 남긴다(`assignment-wrapup` 스킬 방식).
- **T1 확인 결과 (사용자 요청으로 당일 실행):**
  - 기본 Python 3.15.1은 uv가 관리한다. `pip install`은 `externally-managed-environment`로 막혀 있으므로 **uv 가상환경을 쓴다.**
  - `uv venv -p 3.15` + `uv pip install --only-binary=:all: numpy pandas scikit-learn` → 휠 설치 성공(약 11초)
  - 설치된 버전: numpy 2.5.5, pandas 3.1.1, scikit-learn 1.9.1 (scipy 1.18.1, joblib 1.6.0)
  - `HistGradientBoostingClassifier` + `CalibratedClassifierCV` 학습, `permutation_importance` 불러오기 확인
  - 예비안: uv에 Python 3.13.17, 3.12.15도 설치되어 있음
  - 결론: **위험 해소.** 버전은 `ml/requirements.txt`에 위 값으로 고정한다.

## Q9. 현업 검토: 면담 효과와 퇴사 사유 (2026-11-16)

**사용자 의견 (HR 15년 경력):**
- 실제 면담 효과는 사람마다 다르고 크기도 다르다.
- 면담을 정석대로 했고, 면담자 직위가 높을수록(팀장 < 실장 < 본부장 < 대표) 효과가 있다고 경험상 느낀다.
- 사람마다 특성이 달라 통계로 잡아낼 수 있을지 의문이다.
- 면담보다 더 중요한 퇴사 사유: ① 만족하는 연봉 수준 ② 하고 싶은 업무를 하는지 ③ 급여 외 복지 등 보상 만족 ④ 팀장 등 주변인 갈등 ⑤ 회사의 방향성·성장
- 질문: 면담에 기반한 분석이 의미가 있는가?

**논의 정리:**
1. 경험은 업리프트의 전제(효과의 이질성)를 뒷받침한다. 시나리오 B가 현실에 가깝다.
2. 빠진 축 두 가지:
   - 면담자 직위는 사람 특성이 아니라 **처치의 종류**다. 질문이 "누구를 면담할까" → "**누구를 누가 면담할까**", 실무적으로는 "**한정된 임원 면담 슬롯을 누구에게**"가 된다.
   - **사유 × 면담자 권한의 궁합**이 효과를 만든다. 직위가 높을수록 효과가 큰 이유는 사유를 해결할 권한(처우 조정, 부서 이동, 비전 공유)이 있기 때문이다. 팀장 갈등이 사유면 팀장 면담은 역효과일 수 있다.
3. 통계는 개인을 맞히지 못한다. 그러나 예산 제약 하의 **줄 세우기는 무작위보다 낫기만 하면 이득**이다. 도구는 순서를, 사람은 면담에서 실제 사유를 판단한다(교안: 판단은 사람).
4. HR 실무 주의점: 사유 데이터는 주로 조직문화 진단에서 온다. **익명 약속 설문을 개인 선정에 쓰면 신뢰가 깨진다.** 팀장 갈등은 기명 시 축소 보고되기 쉽다. 실무에서는 면담(stay interview)에서 사유를 확인하는 용도가 많다 → §11 윤리와 보고서에 반영.
5. 면담의 질(정석 여부)은 데이터화가 어려워 모델에 넣지 않고 보고서 한계로 기록.
