# 설계 문서 — 면접 한 번에

> 2026-11-03 · PRD의 "무엇을"을 "어떻게"로 옮긴 문서예요. 기술은 후보를 비교해 고르고 이유를 남겨요.

## 1. 기술 선택

### 고르는 조건 (PRD 8장)
무료로 시작, 다른 기기에서 열리는 공개 주소, 재배포 후에도 데이터 유지, **2026-11-04 오전까지 완성**, 규칙 R1~R9를 데이터 저장 쪽에서 막을 수 있을 것.

### 후보 비교

| 기준 | A. Supabase + 정적 화면(GitHub Pages) | B. Node 서버 + SQLite (Render) | C. Firebase + 정적 화면 |
|---|---|---|---|
| 동시 예약 1명만(R1) | Postgres 고유 제약 + 행 잠금으로 확실 | SQLite 트랜잭션으로 가능 | 트랜잭션 가능하나 규칙 문법을 새로 익혀야 함 |
| 권한(R6·R7) | RLS + 토큰 함수, 7번 todo에서 경험 | 서버 코드로 직접 구현 | 보안 규칙 언어를 새로 익혀야 함 |
| 데이터 유지 | 외부 DB라 재배포와 무관 | Render 무료 디스크는 재시작 때 사라질 수 있음 | 외부 DB |
| 운영할 서버 | 없음 | 있음 (무료 서버는 잠들었다 깨는 데 시간 걸림) | 없음 |
| 오늘 안에 끝낼 수 있나 | 높음 (경험 있음, 서버 없음) | 보통 | 낮음 (처음 써 봄) |

**채택: A.** 규칙을 DB 제약·잠금·RLS로 확실하게 막을 수 있고, 운영할 서버가 없으며, 7번 todo 과제에서 써 본 도구라 마감 안에 끝낼 수 있어요.
**기각: B**는 무료 서버의 디스크가 재시작 때 사라질 수 있어 "재배포 후 데이터 유지" 조건이 불안하고, 권한을 서버 코드로 직접 짜야 해요. **C**는 처음 쓰는 규칙 언어라 하루 안에 검증까지 끝내기 어려워요.

### 트레이드오프 (알고 고른 약점)
- **업무 규칙이 SQL 함수에 있어요.** 화면 코드보다 읽기 어렵지만, 화면을 우회한 요청도 똑같이 막혀요. 대신 함수마다 막는 규칙을 주석으로 달았어요.
- **링크를 가진 사람은 그 링크의 일을 할 수 있어요.** 링크 토큰은 추측이 사실상 불가능한 무작위 값(UUID v4)이고, 링크마다 할 수 있는 일은 자기 체크·자기 예약뿐이에요. 링크가 새면 담당자가 그 면접관·후보자를 지우고 새로 만들어요.
- **Supabase 무료 프로젝트는 오래 안 쓰면 일시 정지될 수 있어요.** 한도와 조건은 가입 직전 공식 요금 페이지에서 다시 확인해요.

### 화면 도구: 프레임워크 없이 HTML·CSS·JavaScript (4번 교안의 고르는 기준)
- 화면이 3개(담당자·면접관·후보자)뿐이고 하루 안에 끝내야 해서, 빌드 도구가 필요 없는 순수 HTML·CSS·JS를 골랐어요.
- Supabase 접속은 공식 라이브러리 `@supabase/supabase-js`를 CDN에서 버전 고정으로 불러와요.
- 기각: React·Next.js는 컴포넌트 재사용 이점보다 설정·빌드·배포 경로가 늘어나는 비용이 커요.

### 키 관리 (R8)
- 브라우저에는 **공개 키(publishable/anon)만** 넣어요. 공개 키는 원래 브라우저에 보이는 값이고, 데이터 보호는 RLS와 토큰 함수가 맡아요. 정적 사이트라 빌드 단계가 없으므로 `assets/config.js`에 두고 커밋해요.
- 비밀 키(service_role)는 어디에도 쓰지 않아요. 규칙 시험도 일반 사용자 로그인과 링크 토큰으로만 해요.
- 시험용 담당자 계정의 이메일·비밀번호는 `.env`(커밋 안 함)에만 둬요.

## 2. 데이터 설계

```
positions (포지션: 담당자 1명이 소유, 필요 면접관 수 2·3)
 ├─ interviewers  1:N  (이름, 개인 링크 토큰)
 ├─ candidates    1:N  (이름, 개인 링크 토큰)
 └─ slots         1:N  (시작, 길이 15분 단위, 끝=자동 계산)
       ├─ availability  N:M  slots ↔ interviewers  (면접관의 가능 체크)
       └─ bookings      1:1  slots ↔ candidates    (예약: 슬롯당 1, 후보자당 1)
```

## 3. 규칙을 막는 곳

| 규칙 | 막는 곳 |
|---|---|
| R1 한 시간에 한 명 | `bookings.slot_id` UNIQUE + `book_slot()`이 슬롯 행을 잠그고 확인 |
| R2 링크 하나에 예약 하나 | `bookings.candidate_id` UNIQUE, 다시 고르면 같은 행을 옮겨 '변경' |
| R3 면접관 부족 시간 | `book_slot()`이 가능 체크 수 ≥ 필요 인원 확인, 후보자 화면에도 안 보임 |
| R4 예약된 시간 체크 해제 | `set_availability()`가 예약 여부 확인 (같은 슬롯 행 잠금으로 예약과 동시에 안 일어남) |
| R5 지난 시간 | `book_slot()`이 시작 시각 확인 |
| R6 담당자 데이터 | 모든 표 RLS(소유자만), 예약·체크는 담당자도 직접 추가 불가 |
| R7 링크로는 자기 것만 | anon은 표 접근 권한 없음, 토큰을 받는 함수 4개로만, 이름은 자기 것만 돌려줌 |
| R8 비밀값 | `.env`는 `.gitignore`, 브라우저엔 공개 키만 |
| R9 겹침·15분 단위 | `slots` 배제 제약(EXCLUDE, btree_gist) + CHECK |

## 4. 화면과 주소

| 화면 | 주소 | 하는 일 |
|---|---|---|
| 담당자 | `index.html` | 로그인, 포지션·면접관·후보자·시간 만들기, 링크 복사, 현황 보기, 예약 취소 |
| 면접관 | `interviewer.html?t=토큰` | 시간 목록에서 가능 체크 |
| 후보자 | `candidate.html?t=토큰` | 열린 시간 중 예약·변경 |

화면 코드는 `assets/`에 있어요: `app.js`(공용), `owner.js`, `interviewer.js`, `candidate.js`, `styles.css`, `config.js`(Project URL·공개 키).
