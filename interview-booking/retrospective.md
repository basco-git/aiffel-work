## 1. 왜 이 서비스를 골랐나

HR 15년 동안 가장 자주 반복한 일이 면접 시간 조율이었어요.

- 후보자 한 명을 잡으려면 면접관 2~3명에게 가능한 시간을 묻고, 답이 모이면 다시 후보자에게 전달해요.
- 한 명이 시간을 바꾸면 처음부터 다시 맞춰야 해요.
- 같은 시간에 두 후보자가 겹쳐 잡히는 일도 있었어요.

그래서 "일정 조율 도구"가 아니라 **"면접관이 모인 시간만 후보자에게 보여 준다"** 를 서비스의 중심에 두었어요.

## 2. 무엇을 자르고 무엇을 남겼나

| 구분 | 내용 |
|---|---|
| 남긴 것 (Must 3) | ① 시간 후보 만들기 + 면접관 체크 ② 필요 인원이 모인 시간만 열림 + 후보자 예약 ③ 담당자가 한 화면에서 현황 보기 |
| 먼저 붙인 것 (Should) | 후보자의 시간 **변경** — 현업에서 변경 요청이 가장 잦아서 |
| 자른 것 (Won't) | 캘린더 연동, 메일·문자 자동 발송, 평가표·합격 관리, 화상면접 링크, 회의실 예약, 다국어·결제 |

가장 아까웠던 건 **캘린더 연동**이에요. 면접관 캘린더를 읽으면 체크 자체가 필요 없으니까요. 하지만 OAuth·권한·동기화까지 하루 안에 검증할 수 없다고 판단했고, 대신 **면접관에게 링크를 보내 체크만 받는** 방식으로 문제의 대부분을 해결했어요.

## 3. 어떤 AI 도구로 어떻게 만들었나

사용량과 작업 성격에 따라 도구를 바꿔 가며 만들었어요.

| 단계 | 도구 | 한 일 |
|---|---|---|
| 기초 | **Claude Code** | 주제 비교, PRD(규칙 R1~R9), 작업 규칙(AGENTS.md·CLAUDE.md), 기술 선택(design.md), DB 스키마와 로컬 규칙 시험 |
| 개발 | **opencode + DeepSeek v4.1** | 화면 3개, 실제 Supabase 규칙 시험 스크립트, 제출 문서, GitHub Pages 배포 |
| 후속 개발 | **opencode + Pules Alpha** | 회원가입·승인과 담당자 공유, 목록 화면 개선, 브랜드 로고, 확정 일정 표시, 뒤로가기 처리, 승인 취소 |
| 최종 확인 | **Claude Code** | 변경 내용 점검, 공유·승인 규칙 재검증(R6, 25/25), 제출 전 점검, 상황별 캡처, 회고 정리 |

여러 도구를 오가도 같은 기준으로 일할 수 있었던 건, **규칙을 `AGENTS.md` 한 곳에 두고**(opencode도 이 파일을 읽어요) **진행 기록(`docs/progress.md`)과 인수인계 문서(`docs/handoff.md`)를 커밋마다 남긴** 덕분이에요. 새 도구에서도 "handoff.md 읽고 이어서"로 바로 이어 갈 수 있었어요.

## 4. 가장 기억에 남는 오류 — 포지션 상세 화면이 저절로 목록으로 돌아감

### 증상
포지션 상세 화면을 열어 두고 **아무것도 하지 않고 기다리기만 해도**, 몇 초 뒤 첫 화면인 포지션 목록으로 저절로 넘어갔어요. 면접관·후보자를 추가하려다 화면이 사라지니 서비스를 쓸 수 없는 수준이었어요.

### 헛짚은 시도 (opencode + Pules Alpha)
수정을 요청했지만 모델은 원인을 찾지 못하고 "뒤로가기 동작"을 의심하며 증상만 막았어요. 20여 분 동안 커밋 6개가 쌓였어요.

| 시각 | 커밋 | 시도 | 결과 |
|---|---|---|---|
| 17:14 | `b1421f1` | 트랙패드 가로 스와이프로 이탈하지 않게 | 그대로 |
| 17:19 | `4fb976b` | 스와이프 오작동 추가 방지 | 그대로 |
| 17:21 | `1c2b832` | 세로 overscroll도 뒤로가기로 보지 않게 | 그대로 |
| 17:25 | `9c0276f` | 상세 화면에서 뒤로가기·스와이프를 전부 무시 | 그대로 |
| 17:31 | `a2925a9` | 상세 화면을 서비스가 유지하도록 고정 | 그대로 |
| 17:37 | `9554dad` | **자동 갱신이 상세를 목록으로 덮던 오류 수정** | **해결** |

"가만히 있어도 넘어간다"는 증상은 사용자 입력(스와이프·뒤로가기)과 관계가 없다는 신호였는데, 모델은 그 단서를 쓰지 못하고 토큰만 소비했어요.

### 진짜 원인
담당자 화면은 다른 담당자의 변경을 반영하려고 **5초마다 포지션 목록을 다시 불러와요.** 이때 "지금 보던 포지션의 ID"를 넘겨야 하는데, 코드는 `true`라는 값을 넘기고 있었어요.

```js
// 고치기 전: true 를 '유지할 포지션 ID'로 받아서, 그런 ID가 없으니 목록으로 돌아감
loadPositions(true);
const requested = keepId || options.currentId || previous;

// 고친 뒤: 지금 보던 포지션 ID를 넘기고, 문자열일 때만 ID로 씀
loadPositions(state.position && state.position.id);
const requested = typeof keepId === "string" ? keepId : options.currentId || previous;
```

5초 주기 → 상세에서 목록으로 → "가만히 있어도 넘어간다"가 정확히 맞아떨어졌어요. 고친 줄은 단 3줄이었어요.

### 어떻게 잡았나
모델에게 계속 맡기지 않고, **직접 개발자 도구로 반복 테스트**하며 "몇 초 뒤에 넘어가는지", "무엇을 하지 않아도 넘어가는지"를 확인했고, **인터넷 검색**을 함께 활용해 원인을 좁혔어요. 결국 5초 주기의 자동 갱신이 원인으로 드러났어요.

### 배운 점
- **증상을 정확히 관찰하는 게 먼저예요.** "언제·무엇을 하지 않아도" 일어나는지가 원인을 가리켜요. 교안 8번의 "막히면 되돌리고 리셋"과 "고무 오리에게 설명하기"가 바로 이 상황이었어요.
- **같은 방향의 수정이 두 번 실패하면 멈춰야 해요.** 이번엔 6번까지 갔어요. `AGENTS.md`에 "같은 문제를 두 번 고쳐도 안 되면 멈추고 요약해 보고"라는 규칙이 있었는데도 도구가 지키지 않았어요.
- **모델마다 디버깅 능력 차이가 커요.** Pules Alpha는 테스트 단계 모델로 알고 있는데, 화면 생성은 빨랐지만 원인 추적은 약하다는 걸 직접 겪었어요. 이후 오류 수정과 최종 확인은 Claude Code로 돌아와서 했어요. 앞으로는 **새 기능은 빠른 모델, 원인 추적과 검증은 믿을 만한 모델**로 나눠 쓰려고 해요.

## 5. 그 밖에 막혔던 곳

| 문제 | 원인 | 해결 | 배운 점 |
|---|---|---|---|
| 규칙을 화면에서 막으려 함 | 버튼을 숨겨도 링크로 직접 요청하면 그만 | 예약·체크를 SQL 함수로, 슬롯 행 잠금, 표에 RLS | 문지기는 화면이 아니라 DB |
| 시험이 엉뚱한 이유로 통과 | 로컬 psql의 한글 깨짐과 줄 끝 `\r` 때문에 생긴 오류가 "거부됨"으로 찍힘 | 기대한 거부 문구가 있을 때만 통과로 침 | 실패 시험은 *왜* 실패했는지까지 확인 |
| 규칙을 바꾸고 시험은 그대로 | 공유·승인으로 바꾼 뒤에도 PRD에 옛 R6 "통과"가 남음 | 승인 대기 계정 C를 추가해 R6 7개로 재시험(25/25) | 기능을 바꾸면 시험과 기록도 함께 (AGENTS.md 규칙으로 추가) |
| 화면이 하얗게 빔 | 스크립트가 멈추면 빈 화면만 남음 | 첫 화면에 "불러오는 중…"을 두고 준비되면 감춤 | 실패해도 원인이 보이게 |
| 마감 전 스코프 크립 | 마감 전날 공유·승인·브랜드·뒤로가기 수정이 연달아 붙음 | 점검 뒤 기능 추가를 멈추고 검증·제출만 | Won't 목록은 마지막 날 더 중요 |

## 6. AI를 어떻게 썼나

- **맡긴 일**: PRD 구조, 기술 후보 비교, SQL 스키마·함수, 화면, 규칙 시험 스크립트, 문서 정리, 캡처
- **직접 한 일**: 주제 결정, 현업 요구 반영(면접관 2~3명 일정, 15분 단위, 담당자 공유), Supabase 프로젝트·시험 계정, 도구 선택과 전환, 화면 오류의 원인 추적
- **검증한 방법**: AI가 "된다"고 한 것을 그대로 믿지 않고 ① 로컬 PostgreSQL에서 실제 요청 19개 ② 실제 Supabase에 규칙 시험 25개 ③ 배포 주소에서 성공 조건 3개를 직접 클릭 ④ 제출 전 점검 스크립트(링크·비밀값·이미지·README·푸시 상태) 순서로 확인했어요.

## 8. 교안 회고 질문

**Q1. 오늘 "자르기"가 가장 아까웠던 기능은? 그래도 자른 이유는?**
캘린더 연동이에요. 면접관의 체크 자체를 없앨 수 있는 기능이지만, OAuth·권한·동기화를 하루 안에 검증할 수 없었어요. 링크로 체크만 받는 방식이 핵심 문제(면접관이 모인 시간만 열기)를 먼저 풀어 줬어요.

**Q2. 막혔을 때 나를 가장 도와준 규율은? (한 번에 하나 / 작동하면 저장 / 막히면 리셋 / 이해한 것만 배포)**
**작동하면 저장(커밋)** 이에요. 커밋마다 확인한 결과를 메시지로 남겨서, 도구를 세 번 바꿔도 어디까지 됐는지 바로 알 수 있었어요. 반대로 포지션 상세 오류 때는 **막히면 리셋**을 늦게 지켜서 헛된 커밋 6개를 쌓았어요. 다음엔 두 번 실패하면 멈추고 증상부터 다시 관찰할 거예요.

**Q3. 완성까지, 지금 가장 겁나는 부분은 무엇인가?**
실제 사용자를 받는 것이에요. 지금은 링크를 가진 사람이 그 링크의 일을 할 수 있는 구조라, 링크가 새면 담당자가 사람을 지우고 새로 만들어야 해요. 실제 지원자 정보를 다루려면 링크 만료, 접근 기록, 개인정보 보관 기간까지 갖춰야 해서 그 부분이 가장 부담돼요.
