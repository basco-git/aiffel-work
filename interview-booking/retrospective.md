# 회고 — 면접 한 번에

> 2026-11-03 · Main Quest 01 「내 서비스 만들기」
> 한 문장: **면접관 2~3명의 일정이 모인 시간만 후보자에게 열리는 예약 페이지**를 하루 안에 기획·구현·(배포)까지 해 봤어요.

## 1. 왜 이 서비스를 골랐나

HR 15년 동안 가장 자주 반복한 일이 면접 시간 조율이었어요. 후보자 한 명을 잡으려면 면접관 2~3명에게 가능한 시간을 묻고, 답이 모이면 다시 후보자에게 전달하고, 한 명이 시간을 바꾸면 처음부터 다시 맞춰야 했어요. 게다가 같은 시간에 두 후보자가 겹쳐 잡히는 일도 있었어요.

그래서 "일정 조율"이 아니라 **"면접관이 모인 시간만 후보자에게 보여 준다"** 를 서비스의 중심에 두었어요. 이 한 문장이 흔들리면 기능을 아무리 많이 넣어도 이 서비스가 아니게 돼요.

## 2. 무엇을 자르고 무엇을 남겼나

**자른 것 (Won't)**: 구글·아웃룩 캘린더 연동, 메일·문자 자동 발송, 면접 평가표·합격 관리, 화상면접 링크 자동 생성, 회의실 예약, 다국어·결제.

가장 아까웠던 건 캘린더 연동이에요. 면접관이 이미 쓰는 캘린더를 읽으면 체크 자체가 필요 없어요. 하지만 OAuth·권한·동기화까지 하루 안에 검증할 수 없다고 판단했어요. 대신 **면접관에게 링크를 보내 체크만 받는** 방식으로 문제의 80%를 해결했어요.

**남긴 것 (Must 3)**: ① 시간 후보 만들기 + 면접관 체크 ② 필요 인원이 모인 시간만 열림 + 후보자 예약 ③ 담당자가 한 화면에서 현황 보기. 여기에 후보자의 시간 **변경**을 Should로 넣었어요. 현업에서 변경 요청이 가장 잦았기 때문이에요.

## 3. 막혔던 곳과 푼 방법

**① 규칙을 화면에서 막으려던 생각을 버림**
처음에는 "버튼을 숨기면 되지 않을까" 했는데, 링크를 복사해 직접 요청을 보내면 그만이에요. 그래서 예약·체크를 SQL 함수로 만들고, 슬롯 행을 잠그고, 표에는 RLS를 걸었어요. 화면 코드를 우회해도 DB가 거부하는 것을 로컬 시험 19개로 확인했어요. 대신 SQL이 화면 코드보다 읽기 어려워서, 함수마다 "이 함수가 막는 규칙"을 주석으로 달았어요.

**② 시험이 엉뚱한 이유로 통과함**
로컬 PostgreSQL 시험에서 한글이 깨지고(`PGCLIENTENCODING`), psql 출력 끝의 `\r` 때문에 UUID가 거부됐어요. 그 오류가 "거부됨"으로 찍혀서 **실패해야 할 시험이 통과**하는 것처럼 보였어요. 기대한 한국어 오류 문구가 있을 때만 통과로 바꾸고 나서야 진짜 결과(19/19, 동시 예약 10건 중 1건)가 보였어요. "통과"의 기준을 먼저 정하는 게 얼마나 중요한지 배웠어요.

**③ 화면이 하얗게 비는 문제**
모든 영역을 자바스크립트로 열게 만들면, 스크립트가 한 번 멈출 때 빈 화면만 남아요. 첫 화면에 "불러오는 중…"을 두고 준비되면 스크립트가 감추게 했어요. 실패하면 그 글이 남아서 원인을 알 수 있어요.

## 4. AI를 어떻게 썼나

- **맡긴 일**: PRD 초안 구조, 기술 후보 비교, SQL 스키마·함수, 화면 3개, 규칙 시험 스크립트, 문서 정리.
- **직접 한 일**: 주제 결정, "면접관 2~3명 일정도 함께" 같은 현업 요구 반영, Supabase 프로젝트 생성과 시험 계정, 배포 여부 결정.
- **검증한 방법**: AI가 "된다"고 한 것을 그대로 믿지 않고 ① 로컬 PostgreSQL에서 실제 요청 19개 ② 브라우저 미리보기에서 버튼 동작 ③ (예정) 실제 Supabase에 같은 시험을 다시 보내는 순서로 확인했어요.
- **아쉬운 점**: Supabase 프로젝트를 첫날 먼저 만들었으면 실제 DB 시험을 더 일찍 했을 텐데, 화면을 가짜 데이터로만 확인해 실제 연결 검증이 마감 직전으로 밀렸어요.

## 6. 교안 회고 질문에 대한 답

> 교안에 적힌 질문 문구와 순서가 다르면 알려 주세요. 답은 그대로 옮겨 쓸 수 있게 주제별로 나눠 두었어요.

**Q1. 이번 과제에서 가장 오래 고민한 결정은 무엇이고, 왜 그렇게 정했나?**
기술 선택이었어요. Node 서버 + SQLite는 익숙하지만 무료 서버의 디스크가 재시작 때 사라질 수 있어 "재배포해도 데이터가 남는다"는 조건이 불안했어요. Firebase는 규칙 언어를 새로 익혀야 해서 하루 안에 검증까지 못 갈 것 같았고요. 이미 써 본 Supabase를 골라 규칙을 DB에 맡겼어요.

**Q2. AI가 만든 결과를 어디까지 믿었고, 어떻게 확인했나?**
코드는 믿고 쓰되 "동작한다"는 말은 믿지 않았어요. 규칙은 실제 요청으로, 화면은 브라우저에서 버튼을 눌러, 데이터는 새로고침 뒤에도 남는지로 확인했어요. 시험 스크립트가 엉뚱한 이유로 통과했던 경험 때문에, 이제는 실패해야 하는 경우도 함께 시험해요.

**Q3. 같은 과제를 다시 한다면 무엇을 먼저 바꾸겠나?**
외부 서비스(DB·배포)를 **첫 시간 안에** 연결해 두겠어요. 화면부터 만들면 보기에는 빨라 보이지만, 실제 연결에서 생기는 문제(권한·키·URL)를 마지막에 몰아서 겪게 돼요. 이번에도 그랬고요.
