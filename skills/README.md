# 내가 실제로 쓰는 Claude Code 스킬

과제를 하면서 AI에게 매번 반복해서 시키던 일 세 가지를 스킬로 만들었습니다.
모두 2026-11-02 todo 과제(7-1 Subquest)를 제출하며 실제로 겪은 불편에서 나왔습니다.

| 스킬 | 이럴 때 한마디로 | 하는 일 | 왜 만들었나 |
|---|---|---|---|
| [submit-check](submit-check/) | "제출 전 점검해 줘" | 문서 링크가 git에 있는지, 비밀값·이미지 위치 정보, 맨 위 목록, 푸시 상태를 스크립트로 점검 | 스킬 파일이 `.gitignore`에 걸려 저장소에 빠진 채 제출할 뻔함 |
| [evidence-capture](evidence-capture/) | "캡처 찍어 줘" | 실제 실행 결과를 HTML로 다시 그려 PNG로 저장, 높이 자동, 제출 문서 표에 추가 | 캡처마다 스타일을 다시 찾고, 높이가 잘려 다시 찍음 |
| [assignment-wrapup](assignment-wrapup/) | "과제 정리해 줘" | 맨 위 README 표에 한 줄, 진행 과정·회고는 과제 폴더 README에 | 회고가 맨 위 README에 쌓여 목록이 안 보였음 |

세 스킬은 한 흐름으로 이어집니다: **캡처 만들기 → 과제 정리 → 제출 전 점검 → 커밋·PR**.

## 왜 만들었나

과제를 하나 끝낼 때마다 AI에게 비슷한 부탁을 여러 번 했습니다. "빠진 거 없나 봐 줘", "이 장면 캡처해 줘", "README에 정리해 줘". 그런데 부탁할 때마다 AI가 확인하는 항목, 캡처 모양, 정리하는 방식이 조금씩 달랐고, 그 틈에서 실수가 나왔습니다.

2026-11-02 todo 과제(7-1 Subquest)를 제출하며 실제로 겪은 일입니다.

- **저장소에 빠진 채 제출할 뻔함**: 캡처에는 나오는 스킬 파일이 `.gitignore`(`.claude/` 전체 제외) 때문에 저장소에 아예 없었습니다. 제출 직전에 우연히 발견했습니다.
  → `submit-check`: 문서에 건 링크·이미지가 실제로 git에 올라갔는지, 비밀값·위치 정보, 목록, 푸시 상태를 매번 같은 다섯 가지 기준으로 확인합니다.
- **캡처를 다시 찍음**: 캡처를 부탁할 때마다 HTML과 스타일 파일을 새로 찾았고, 고정 높이로 찍어 아래가 잘리는 바람에 C5를 두 번 찍었습니다.
  → `evidence-capture`: 템플릿을 스킬에 넣고, 내용 높이를 먼저 잰 뒤 찍습니다. 실제로 실행한 결과만 그리고, 다시 그린 화면이라고 문서에 밝힙니다.
- **README에서 과제 목록이 안 보임**: "README에 정리해 줘"를 반복하다 보니 회고 4개가 맨 위 README에 쌓였습니다. AI가 쓴 회고에 내가 확인하지 않은 일이 "겪었다"고 적힌 적도 있습니다.
  → `assignment-wrapup`: 맨 위 README는 목록, 자세한 내용은 과제 폴더 README에 쓰고, 회고에는 확인된 사실만 씁니다.

### 무엇을 스킬로 만들고 무엇을 뺐나

반복한 지시를 모두 스킬로 만들지는 않았습니다.

- 한국어로 답하기, 작업 완료 알림, 삭제 전 확인처럼 **언제나 지켜야 하는 규칙**은 이미 훅과 규칙 파일이 맡고 있어서 뺐습니다.
- 제출 전 점검, 캡처, 과제 정리처럼 **필요할 때 꺼내 쓰는 작업 절차**만 스킬로 만들었습니다.
- 매번 결과가 같아야 하는 부분(점검 항목, 캡처 높이)은 AI 판단에 맡기지 않고 스크립트로 만들었습니다. AI는 스크립트를 돌리고 결과를 설명하는 일만 합니다.

### 만든 뒤 실제로 써 보니

- 만든 날 바로 이 README를 정리하는 데 세 스킬을 모두 썼습니다. 문서에 적지 않은 말투("제출 전 정리해줘")에도 `submit-check`가 불렸습니다([C1](docs/screenshots/C1-submit-check-run.png)).
- 맨 위 README의 절을 과제 폴더로 옮기면서, `#앵커`가 붙은 링크는 점검하지 못한다는 것을 알게 되었습니다. 그래서 `submit-check`에 앵커 확인을 추가했습니다. 스킬은 한 번 만들고 끝나는 것이 아니라, 쓰면서 고쳐 가는 것이었습니다.

## 설치

Claude Code는 `.claude/skills/<스킬 이름>/SKILL.md`를 스킬로 읽습니다. 이 폴더(`skills/`)가 원본이고, 설치 스크립트가 개인 스킬 폴더 `~/.claude/skills/`로 복사합니다. 개인 스킬 폴더에 두면 **모든 프로젝트**에서 발동합니다.

```bash
python -I skills/install.py            # 전부 설치 (이미 있으면 덮어씀)
python -I skills/install.py --check    # 설치본이 이 저장소와 같은지 확인
```

- 스킬을 고친 뒤에는 다시 설치해야 반영됩니다. `--check`가 "다름"을 알려 줍니다.
- 한 프로젝트에서만 쓰려면 스킬 폴더를 그 프로젝트의 `.claude/skills/` 아래로 복사해도 됩니다.
- 스크립트는 Python 3.9 이상(표준 라이브러리만), `evidence-capture`는 Chrome이나 Edge가 필요합니다.

### 회고 (8. 스킬 만들기)

- 스킬 거리를 따로 고민하지 않고, 바로 전에 한 과제(todo 7-1)에서 AI에게 여러 번 시킨 일을 골랐더니 "왜 만들었나"가 날짜와 실제 사건으로 바로 설명됨.
- 반복 지시라고 다 스킬은 아니었음. 한국어로 답하기, 알림, 삭제 전 확인처럼 **항상 지켜야 하는 규칙**은 훅·규칙 파일로, 제출 점검처럼 **가끔 하는 작업 절차**는 스킬로 나누는 것이 기준이 됨.
- description에 "언제 쓰는지 + 내가 실제로 할 말 예시 + 쓰지 않는 경우"를 넣었더니, 새 세션에서 스킬 이름을 말하지 않아도 3번 중 3번 모두 맞는 스킬이 불렸음. 말투를 바꾼 2차 시험에서도 같았음.
- 점검과 캡처처럼 결과가 매번 같아야 하는 부분은 AI 판단에 맡기지 않고 스크립트로 만들었음. AI는 스크립트를 돌리고 결과를 설명하는 역할만 하니 기준이 흔들리지 않음.
- 만든 점검 스킬을 스킬 폴더 자체에 먼저 써 보니, 커밋 전 새 파일까지 "문제"로 보는 오판이 바로 드러남. 만든 도구를 내 작업에 먼저 써 보는 것이 가장 빠른 시험이었음.
- 캡처 스킬은 편한 만큼 꾸며 낼 위험도 있어서 "이번 대화에서 실제로 실행한 결과만 그린다, 다시 그린 화면이라고 밝힌다"를 절차에 넣었음.
- `.claude/skills/`는 Claude Code가 읽는 위치지만 GitHub에서는 숨은 폴더처럼 보여 눈에 잘 띄지 않았음. 원본은 맨 위 `skills/`에 두고 설치 스크립트로 개인 스킬 폴더에 복사하는 방식으로 바꿨더니, 저장소 밖에서도 발동하게 됨. 대신 스킬을 고치면 다시 설치해야 해서 `--check`로 차이를 확인하게 함.
- 발동 시험은 새 세션을 화면 없이(`claude -p`) 열어 했음. 파일을 바꾸지 않게 쓰기 도구를 막고 턴 수를 제한하니 안전하게 반복할 수 있었고, 비용은 1차 약 1달러, 2차 약 0.56달러였음.
- 아쉬운 점: 마크다운 파일을 직접 작성해 보면 더 좋았을 것 같음. 초보자라 Claude와 함께 작성하고, 수정 내역이 반영되었는지 꼼꼼히 확인했음. 다음엔 이번 경우를 바탕으로 직접 작성도 해 볼 수 있을 것 같음.
