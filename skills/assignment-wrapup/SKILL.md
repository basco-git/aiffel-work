# 과제 제출 정리

정리 원칙은 하나다. **맨 위 README는 목록, 자세한 내용은 과제 폴더 README.**
채점자는 맨 위 표에서 과제를 찾고, 링크를 눌러 들어가 진행 과정과 회고를 본다.

## 1. 재료 모으기 (사실만)

다음에서 확인된 사실만 모은다. 확인하지 못한 것은 회고에 쓰지 않는다.

- `git log --format='%h %ad %s' --date=format:'%Y-%m-%d %H:%M'`: 무엇을 언제 했는지
- 과제 폴더의 기존 `README.md`, `SUBMISSION.md`, `PRD.md`: 이미 적힌 내용(겹쳐 쓰지 않는다)
- 이번 대화에서 실제로 겪은 일: 오류, 고친 방법, 사용자가 직접 한 일, 사용자가 남긴 말
- 실행 URL(배포·플레이 주소)과 과제 URL(제출 문서나 폴더)

## 2. 맨 위 README: 표에 한 줄

저장소 맨 위 `README.md`의 과제 표에 한 줄만 추가한다. 표가 없으면 아래 모양으로 만든다.

```markdown
| # | 프로젝트 | 요약 | 실행 | 과제 |
|---|---|---|---|---|
| 7 | todo | 할 일 앱: 로컬 SQLite → Supabase·로그인·RLS 전환 | [실행](https://...) | [제출 문서](todo/SUBMISSION.md) |
```

- 요약은 한 줄, 무엇을 만들었는지가 보이게 쓴다.
- 실행 URL이 없으면 `-`를 쓴다. 과제 URL은 제출 문서가 있으면 그 문서, 없으면 폴더.
- 공백이 든 폴더 이름은 `%20`으로 쓴다(`Pair%20Quest-gmae/`).
- 한 과제에 딸린 부과제는 `7-1`처럼 번호를 이어 붙인다.
- 회고·진행 과정·긴 설명은 맨 위 README에 쓰지 않는다. 사용자가 맨 위에 캡처 표 같은 제출 내용을 따로 요청한 경우에만 표 아래에 짧은 절을 둔다.

## 3. 과제 폴더 README: 진행 과정 + 회고

과제 폴더 `README.md` 끝에 두 절을 추가한다(이미 있으면 그 아래에 이어 쓴다).

```markdown
## <과제 이름> 진행 과정

목표: <한 문장>

| 순서 | 한 일 | 결과 |
|---|---|---|
| 1 | ... | ... (확인 장면 번호가 있으면 함께, 예: C1) |

## 회고 (<과제 이름>)

- <겪은 일> → <어떻게 했는지/배운 것>
```

- 진행 과정은 5~10단계로, 결과 칸에 숫자·파일·확인 장면 번호를 넣는다.
- 회고는 기존 회고와 같은 말투(`~했음`, `~함`)로 쓰고, 한 줄에 한 가지만 쓴다.
- 좋았던 점만 쓰지 않는다. 막힌 곳, 실수, 다음에 다르게 할 점을 함께 쓴다.
- 확인하지 못한 일은 단정하지 않는다. 예: 실패를 직접 보지 않았으면 "실패할 수 있어 대비함"으로 쓴다.

## 4. 확인받고 마무리

- 쓴 내용 가운데 추측이 섞일 수 있는 줄(사용자가 겪었는지 모르는 일, 감정, 평가)을 따로 짚어 사용자에게 확인받는다.
- 맨 위 README와 과제 README의 링크가 실제로 열리는지 확인한다. `submit-check` 스킬이 있으면 그것으로 점검한다.
- 커밋·푸시·PR은 사용자가 요청할 때 한다.

## 하지 말 것

- 다른 과제의 회고나 README를 함께 고치지 않는다(사용자가 요청한 경우는 예외).
- 회고 문장을 다듬는다며 사용자가 쓴 회고의 뜻을 바꾸지 않는다. 옮길 때는 그대로 옮긴다.
- 비밀값, 개인 이메일, 계정 정보를 README에 쓰지 않는다.
